# Ticket 29 — restricted same-process Gate runtime

This is an **unaccepted implementation candidate**, governed by the unchanged
[D2 contract](gate-identity-contract.md) and [ADR 0012](adr/0012-gate-identity-and-local-operator-continuation.md).
It does not implement ticket 30 or complete P17. The earlier
[closure-blocker report](ticket-29-closure-blocker.md) describes the archived first attempt, not this candidate.

## Public seam

- Author the existing typed `WorkflowSpec`: nonparallel `Route` edges, one `GateNode`,
  and `TransformNode` declarations with exactly the `done` outcome. Existing spec
  validation still applies. No arbitrary Python callable, Judgment, model operation,
  Loop, Fork or custom state class is admitted here.
- The state is the closed integer `value`, initially `0`. Bind operation keys to
  `RegisteredOperation("add_int_v1", delta)`, with an exact integer delta in
  `[-1000, 1000]`; the key set must exactly match the graph. The retained worker is
  the operation interpreter. Its code, configuration and runtime dependencies are
  executable identity, not the import name or the dataclass's identity.
- `agent_lab.gate_runtime.emit_gate(spec, operations, store=Path(...))` returns a
  `GateVersion`. The owner-only caller-named store must be outside the project and
  Hermes. Canonical spec identity is the workflow identity; bundle digest is its
  immutable executable version. These are internal protocols, not a public spec format.
- `start_gate(version, run_id="demo", driver="graph", mode="operator")` launches
  the retained worker and returns a context-managed `GateRun` with typed `result`,
  `checkpoint`, `events`, and loaded-origin `attestation`. `driver="reference"`
  selects the plain scheduler in a separate worker; it never calls the graph driver.
  The graph driver actually builds and runs `pydantic_graph.GraphBuilder` from
  retained code/configuration. Both schedulers share the closed operation and
  persistence primitives, not each other's execution loop.
- Keep this `GateRun` alive. After the local CLI records a decision, call
  `run.continue_gate()`. Closing the worker never approves or restarts it. A second
  continuation on a completed worker returns the existing result without a new
  step or event. Reopening an existing run ID is refused.

The older general-purpose `compile_reference`, `generate_graph` and
`check_conformance` callable APIs remain unchanged and **do not admit Gate**.
Use the separate restricted public seam; do not pass caller bindings to it.

### Local decision, in another terminal under the store owner's account

```sh
.venv/bin/python -m agent_lab.gate_cli --store /absolute/external/store \
  --run-id demo inspect

.venv/bin/python -m agent_lab.gate_cli --store /absolute/external/store \
  --run-id demo --gate review --pause EXACT_PAUSE \
  --spec EXACT_SPEC_DIGEST --bundle EXACT_BUNDLE_DIGEST approve
```

Use `reject` instead of `approve` for explicit rejection. The CLI re-derives both
identities and the committed pause, requires the explicit scope, derives numeric
UID itself, and records a timestamped owner-only HMAC-authenticated decision.
The per-run key is generated by the worker and held in memory and an owner-only
local file. Identical submissions before consumption return the original record;
conflicting or late submissions fail. The record is printed after durable write
and read-back. There is no remote approval service or caller-supplied approver field.

This is **OS-account trust, not human-person authentication**. A same-UID agent
can invoke the CLI or read its key. An unsigned JSON approval or business-draft
approval is not Gate authority. Offline `mode="fixture"` runs use
`submit_fixture(exact_checkpoint, "approved" | "rejected")`; worker mode is fixed
at startup, and fixture authority cannot authorize an operator run.

## Narrow executable closure

The build-time `gate_capture.py` rehearsal uses isolated CPython (`-I -S -B`) and
an explicit installed dependency root, imports the owned dependencies, and runs
an actual graph. It records loaded Python module origins and native mappings.
Only those files, the native dependencies of observed ELF files, their loader
aliases, the exact CPython executable, and the worker/spec/operation artifacts
are retained. `readelf` supplies the ELF interpreter path; `ldd` supplies native
requirements, with stdout/stderr retained in a refusal. No standard-library
`.so` sweep or installation of optional Tk is performed. Rehearsal is discovery,
**not** proof of successful worker execution.

The launcher rechecks canonical manifest and every referenced blob, then copies
those exact bytes via file descriptors into a private read-only bubblewrap
filesystem. Host `/usr`, the project, site-packages and import caches are not
mounted; only the selected per-run audit directory is writable. Environment is
cleared before worker execution, with isolated imports and no host network
namespace. An absent dependency causes refusal, never ambient fallback.

At startup, Gate, submission, continuation and event completion, the worker
re-derives spec/bundle identity and hashes retained files. It checks actual
`sys.modules` origins and `/proc/self/maps` paths against the retained manifest,
and returns **path → byte digest** evidence for loaded modules and native files.
Frozen/built-in Python code belongs to the retained interpreter/libpython;
OS kernel facilities are trusted. Fixed negative imports demonstrate `_tkinter`
and `tkinter` cannot load. The attestation is also retained inside completed-event
records, not merely printed by the host launcher. Tests compare those origin
hashes against retained blob bytes.

Trusted bootstrap: local emitter/launcher, bubblewrap and OS. This is not a
sandbox against a malicious same-UID controller that rewrites the verifier,
ptraces the worker, or replaces the OS. Normal artifact/evidence alteration is
checked fail-closed; general hostile-Python or portable-environment security is
not claimed. Required platform: Linux CPython, bubblewrap, `readelf`, `ldd`, and a
working installed `pydantic-graph` runtime. Other platforms are refused.

## Commit ordering and checkpoint protocol

Each run has one live worker, exclusively created by its new run directory. The
worker serially consumes commands and retains the exact committed journal bytes.
Every command rechecks journal extent and bytes; it cannot adopt a reconstructed
caller state, repaired history or a second worker for the same run ID.

Audit files are canonical `00000000.json`, `00000001.json`, … envelopes with
`version=1`, `sequence`, `previous`, `kind`, `run_id`, and `data`. `previous` is the
SHA-256 of the prior envelope. Each publication uses an exclusive `.pending-N`
file, file fsync, no-replace hard link to the numbered file, temporary unlink,
and directory fsync. Journal head/sequence advance only after publication. A publication
failure refuses the command; it does not authorize later work or retry the step.

For the budget-3 specimen:

1. `claim(before)` is durable before arithmetic or budget charging.
2. `completed(before/done)` contains resulting state, spend and loaded-origin evidence.
3. `claim(review)` precedes the one charged Gate visit.
4. `completed(review/pending)` **atomically contains the post-Gate checkpoint**,
   pending event and attestation. For operator runs it also contains a
   domain-separated HMAC proof over the entire pending data and preceding
   envelope hash, using the per-run owner-only worker key. The CLI validates
   that committed-prefix proof before recording authority. Only then is
   `PENDING` returned.
5. A fixture decision is a durable `decision` envelope; the operator CLI instead
   atomically publishes authenticated `decision.json`, which the worker validates
   and journals as `decision` on continuation.
6. `resolved(review/approved|rejected)` is durable before successor dispatch.
7. Only approval can produce `claim(after)` then `completed(after/done)`.
   Rejection terminates. Budget exhaustion produces a refusal event without
   arithmetic or an extra charged step.

The typed checkpoint includes protocol version, exact value, used/remaining
budget, run/Gate/random-pause identity, spec/bundle digests, `prior_head` (the
preceding audit claim), and `completed_head` (the semantic event-chain head
including the pending event). The semantic event head is separately domain-separated:
`sha256(b"workflow-generator/gate-event/v1\0" + previous_head.encode() + canonical(event))`.
This avoids a self-referential envelope hash while binding the completed event
prefix. The envelope's own hash is `GateResult.head`. Approval binds the complete
checkpoint. Continuation loads its verified committed representation and charges
no second Gate step. Invalid input produces a refusal rather than a success or an
alternate downstream action.

These are same-process ordering guarantees. No fresh-process reconstruction,
arbitrary-crash recovery, concurrent external state mutation safety, or exactly-once
external side effects have been established. Those must not be inferred from
fsync calls; committed-pause restart and crash tests belong to ticket 30.

## Offline conformance

`agent_lab.gate_conformance.check_gate(spec, operations, version, cases)` checks
an actual retained version against typed `GateCase`/`GateExpected` cases. Each case
supplies separate reference and graph fixture decisions. The checker reads back
the canonical retained journal at pause and completion, verifies its continuity,
semantic event heads, checkpoint and decision order against the observed result.
Both pause-prefix and final observations are compared with hand-authored state,
events and spend, and with each other. Random run/pause IDs are checked locally,
not equated across workers. Matching drivers alone cannot pass a wrong oracle, and mismatching
fixture decisions cannot be silently shared. The checker makes no model or
provider calls. See `tests/test_gate_conformance.py` for executable budget 1/2/3,
pending, approve and reject examples.

Independent Standards and Spec assessments were requested by the controller;
their first passes found approval-time and store-boundary defects, and a final
Spec confirmation of the corrected prefix proof remains pending. See the
separate evidence report for validation results and frozen hash; neither test
success nor this document means ticket acceptance.
